# Правила работы

## С Сергеем

- Отвечай по-русски, на «ты», коротко.
- Код в чат не вставляй: правки только через git, смотреть в diff и в PR.
- PR маленькие, одна задача — один PR, короткое ревью.
- Новая идея начинается с плана и вопросов, не с кода.
- Всё пользовательское — сразу на русском и английском. Админка владельца остаётся на русском. Сообщения бота — на языке игрока.
- Виджеты Bot API — в конце, не раньше согласованной очереди (см. [ROADMAP.md](ROADMAP.md)).
- Docker не используем.
- Деплой теста — только через «Обновить тест». Команды на сервер не гоняй в обход этой кнопки, если Сергей явно не попросил шаг на машине.

## Слияние

- Сливать можно только после явного «мержи» или «да». Голое «ок» — не согласие.
- В отчёте по каждому PR — нумерованный список умолчаний. «Мержи» принимает все пункты списка.
- Одновременно сливается только один PR, всегда в `main`, по цепочке (следующий — после обновления `main`).
- Слитые ветки можно удалять (решение Сергея, 17.11.2026).
- Процедура:

  1. `gh pr checks N` — проверки зелёные.
  2. Сверить head SHA с тем, что ревьюили.
  3. `gh pr merge N --merge --match-head-commit <sha>`.
  4. Обновить [JOURNAL.md](JOURNAL.md) (новый SHA `main`, что вошло, что дальше).
  5. Напомнить Сергею нажать «Обновить тест», если на стенде должно появиться изменение.

## Шаги на сервере

Сергей работает с Windows, не root и не системный администратор. Команды — по одному шагу, копируемые целиком.

- Пиши команды через `printf` и `| sudo tee` (и `sudo tee -a` для дозаписи).
- Не предлагай `nano`, интерактивный редактор и heredoc (`cat <<EOF`) — их неудобно вставлять и легко сломать.
- Не предполагай, что он уже в нужном каталоге или что команда выполнена, пока он не подтвердил.

## Секреты

В репозиторий, в тело PR и в эти документы нельзя класть:

- пароли, токены, ключи (в том числе toncenter), seed-фразы, SSH-ключи;
- IP сервера, URL Postgres, пароли и имена служебных пользователей БД;
- адреса кошельков, Telegram ID владельца.

Перед пушем прогони diff и тело PR: обрывки паролей, адреса кошельков, IPv4, строки подключения к базе, нестандартные порты и служебные имена БД, блоки ключей (`BEGIN`), значения рядом со словами key/token.

Если секрет уже засветился — не повторяй его в чате и не коммить; скажи Сергею отдельно, как ротировать.

## Передача работы между аккаунтами

Два аккаунта Grok Bot могут вести задачи по очереди или параллельно. Чтобы подхватить чужую работу, не нужна переписка из другого чата — нужна эта папка, Issue и PR.

1. **Одна задача = одна ветка = один PR.** Не смешивай две темы в одной ветке.
2. **Перед стартом захвати задачу Issue.** Создай или возьми GitHub Issue, назначь себя, поставь лейбл `in-progress` и напиши, какой аккаунт ведёт работу. Второй аккаунт эту задачу не трогает.
3. **Пушь часто** и сразу открывай **черновик PR** в `main`.
4. В описании PR держи блок «Статус» (есть в [.github/pull_request_template.md](../../.github/pull_request_template.md)):
   - сделано;
   - осталось;
   - следующий шаг;
   - открытые вопросы.
   Обновляй блок после каждого законченного шага.
5. **Чтобы подхватить:** прочитай `docs/agent/`, блок «Статус» в PR, клонируй/обнови ветку, переназначь Issue на себя и укажи свой аккаунт. Не начинай параллельную ветку на ту же задачу.
6. **Решения из любого чата** сразу записывай в `docs/agent/` (обычно [DECISIONS.md](DECISIONS.md) или [ROADMAP.md](ROADMAP.md)) — отдельным маленьким коммитом в ту же ветку или отдельным docs-PR, если задача уже слита.
7. После каждого слияния в `main` обнови [JOURNAL.md](JOURNAL.md).
8. Конфликт захвата: если на задаче уже есть `in-progress` и другой аккаунт — остановись и согласуй с Сергеем.

Лейбл `in-progress` нужно завести в репозитории, если его ещё нет (после слияния этого PR).
